# cqa-grader

Grades a system's retrieval trace against a cqa benchmark: reads the
benchmark's published Turtle, reads a JSON trace of what the system
retrieved and cited per question, dispatches on `answer_kind`, and
reports pass/fail per check. Ships a naive baseline retriever so a
benchmark's CI has something to grade.

## Layout

- `src/benchmark.rs` reads a `cqa:Benchmark` from Turtle (oxigraph, SPARQL)
  or from its LinkML YAML (`panschema-model`); a test keeps the two equal.
- `src/trace.rs` is the trace format, the contract with graded systems.
  `schemas/trace.schema.json` is generated from it and a test keeps them equal.
- `src/grade.rs` scores a trace: four base checks plus one per answer kind.
- `src/baseline.rs` is the naive retriever: label linking, one-hop SPARQL
  lookup, cites everything, never asserts absence (which records a
  negative is about is in the key, not the question). It must never read
  the key; a test checks that.
- `src/main.rs` is the CLI: `grade` (a trace, or `--baseline` run in
  place), `baseline`, `trace-schema`.
- `crates/site/` is the landing site (Leptos CSR, Trunk, Tailwind v4),
  outside the workspace (its own `[workspace]`; run cargo with
  `--manifest-path crates/site/Cargo.toml`, clippy with
  `--target wasm32-unknown-unknown`). `crates/site/preview.sh` serves it
  with hot reload. `public/roadmap.json` is the roadmap. Each Now and Next item
  lists acceptance criteria, each naming its proving test as
  `<path>::<function>`; a test fails if a done item names a test that
  does not exist. Move an item in the commit that does its work.
- `brand/` is the mark, wordmark, palette and fonts; `scripts/gen-brand.py`
  regenerates them.
- `docs/architecture/model.c4` is generated by asbuilt (pinned in
  `asbuilt.toml`); never edit it. After changing modules or what they
  reference, run `asbuilt survey` and commit the result; `asbuilt check`
  runs in the pre-commit hook and CI. `asbuilt docs -o
  crates/site/public/architecture` writes the site's Architecture
  section (`preview.sh` does this).

## Test graphs are generated, then committed

`panschema.toml` consumes wine (ontology-authoring-template) and cqa
(cqa-schema) as `path:` siblings and generates `tests/fixtures/`: two
Turtle graphs, byte-identical to wine's own published `site/artifacts/`,
and the benchmark's LinkML sources (cqa's schema with its imports merged,
and a byte copy of wine's `data/wine-benchmark.yaml`). They are committed
like a lockfile, with `tests/fixtures/PROVENANCE` naming the sibling and
panschema versions they came from, so a fresh clone runs the tests with
neither the siblings nor panschema. Never edit them by hand; regenerate:

```bash
./scripts/regen-fixtures.sh                                         # panschema on PATH
PANSCHEMA=../panschema/target/debug/panschema ./scripts/regen-fixtures.sh
```

The Dogfood workflow (every push to main, and daily) clones the siblings'
`main`, installs panschema from its main SHA, regenerates, runs the
suite, and fails if the graphs differ from the committed ones. Moving the
fixtures forward is a commit of the script's output, reviewed like any
other diff.

## Development

```bash
cargo build              # build
cargo nextest run        # run tests
cargo test --doc         # doc tests
cargo clippy             # lint
cargo fmt                # format
cargo deny --workspace check bans licenses sources   # license/dependency check
prek run cargo-lockpatrol --all-files                # advisories, every Cargo.lock
cargo vet                # supply chain review
cargo run -- trace-schema > schemas/trace.schema.json   # after changing src/trace.rs
```

## Sandbox

Claude Code's sandbox (sandbox-runtime, Seatbelt on macOS) is on
globally. The sibling checkouts are read, never written:
`scripts/regen-fixtures.sh` reads `../ontology-authoring-template` and `../cqa-schema`,
and a panschema debug build is made in panschema's own session.
Anything that needs the Keychain or writes git hooks (`prek install`,
`gh auth`) runs outside the sandbox, by hand.

## Agent skills

The panschema skill is a pinned dependency, the same as `panschema.toml`:
`skills-lock.json` (tracked) records its source and a content hash, and
the installed copy is gitignored. Install it once after cloning, from a
plain terminal (the sandbox denies writes under `.claude/skills/`, and
the CLI reports success even when the write was denied):

```bash
npx skills add padamson/panschema -s panschema-usage -a claude-code -y
ls -l .claude/skills/   # panschema-usage is listed
```

Refresh with `npx skills update -p`, also from a plain terminal: the CLI
writes the skill's directory under `.claude/skills/` itself, with no
`.agents/` copy. It reports success whether or not it wrote anything, so
confirm by reading `metadata.version` in
`.claude/skills/panschema-usage/SKILL.md` against panschema's `main`. A
new session picks up the change.

## Pre-commit hooks

```bash
cargo install prek
prek install --overwrite   # --overwrite replaces any legacy pre-commit hook
```

Hooks mirror CI checks: fmt, clippy, check, nextest, doctest, deny, vet, and
advisories through cargo-lockpatrol (the CI gate's action, and the daily
`advisory-monitor.yml`, which keeps one tracking issue).

## Mutation testing

```bash
./scripts/mutants.sh                 # diff HEAD~1..HEAD (default)
./scripts/mutants.sh main            # diff main..HEAD
./scripts/mutants.sh -- --jobs 4     # pass extra cargo-mutants args
```

`scripts/mutants.sh` wraps `cargo mutants --in-diff`, scoping mutation
testing to just the lines a commit touched. CI runs the per-diff variant
on every push and PR; the full-codebase job is manual-only.

## Manual checks

What a session cannot check and the person reviewing the work can. A
hand-off before a commit names each one that applies, as its command and
what a pass looks like; CI is the backstop, not the plan.

**From a plain terminal** (the sandbox blocks these):

- The pre-commit hook, once per clone: `prek install --overwrite`. A pass
  is `.git/hooks/pre-commit` with `# File generated by prek` as its second
  line.
- The panschema skill, once per clone and after a change to
  `skills-lock.json`: the `npx skills add` in "Agent skills". A pass is
  `panschema-usage` listed by `ls -l .claude/skills/`, and
  `git ls-files .agents/ .claude/skills/` printing nothing.
- A change to `.claude/settings.json`: the sandbox denies writes to it,
  so apply the edit by hand, then run `/sandbox` in a new session. A pass
  is the resolved config showing the change.
- The site, after a change under `crates/site/`: `crates/site/preview.sh`,
  then open the page it serves. A pass is the page building with no Trunk
  or Tailwind error and reading as intended.

**Not from a session at all**, changed on github.com or crates.io: the
required checks in `main`'s branch protection (after adding, renaming or
removing a job that gates a merge), the "release tags" ruleset and the
`release` environment's deployment policies (after a change to
`release.yml`'s tags), the merge App's installation on this repo and its
key, Dependabot malware alerts, and the crate's Trusted Publisher.

**By eye:**

- Prose a reader will act on: the CHANGELOG entry, the README, and the
  site's copy.
- A workflow change: the first run of the changed job on GitHub, since
  nothing local runs it. A job that only fires on a tag, a schedule or a
  Dependabot PR waits for that event, or a `workflow_dispatch` where it
  has one.

## Vocabulary

panschema *verifies* artifacts against their specs. This tool *grades* a
system's output against the key. *Validate* is reserved for the strict
V&V sense and is not used here.

## Release process

1. Update version in `Cargo.toml`
2. Update `CHANGELOG.md`
3. Commit: `git commit -m "Release vX.Y.Z"`
4. Push the commit, `git push origin main`, and wait for Security & Quality
   to pass on it (`release.yml` does not check vet or deny itself).
5. Tag and push the tag: `git tag vX.Y.Z`, then `git push origin vX.Y.Z`

The tag runs `release.yml`: it refuses a commit that is not on `main`,
checks the tag against `Cargo.toml` and the CHANGELOG, runs the semver
gate and the build and tests on four targets, publishes to crates.io
through Trusted Publishing in the `release` environment, and creates the
GitHub Release last.

The first release differs, because crates.io adds a trusted publisher
only to a crate that exists. After step 4, publish by hand (`cargo
publish` from a plain terminal, with a token you revoke afterwards). Then,
on the crate's settings page on crates.io, add a GitHub trusted publisher
(`padamson/cqa-grader`, workflow `release.yml`, environment `release`) and
tick "Require trusted publishing for all new versions". The tag's publish
job then finds the version on crates.io and skips it.
